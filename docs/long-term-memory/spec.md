# KCode 长期记忆二期 Spec

## 背景

KCode 一期已经能保存和恢复会话，并通过 `KCODE.md` 加载人工编写的指令，但不会从历史互动中形成可跨会话复用的长期知识。用户每次开启新会话时，KCode 虽然能够恢复旧会话，却不会自动理解哪些偏好、纠正经验、项目事实或参考资料值得在未来继续使用。

二期要建立的不是“把所有历史重新塞给模型”，而是从成功完成的对话中发现候选知识，经用户确认后持久化，并在后续会话中自动使用。会话日志仍是历史证据，长期记忆是经过确认的知识提炼，两者职责不同。

## 目标

- 新会话能够使用过去确认的用户偏好、纠正经验、项目事实和参考资料。
- 模型只能提出候选，不能自行创建、更新、合并、失效或删除长期记忆。
- 记忆的来源、作用域、状态和修改时间可以检查；错误记忆可以失效、恢复或由用户永久删除。
- 记忆提取、治理或存储失败时，正常聊天与一期会话存档仍能继续工作。
- 二期以后台流程和 `Ctrl+M` 面板为中心，不通过增加 `/memory` 等命令代替记忆能力。
- 升级后默认不启用额外模型调用和明文知识留存，必须由用户显式开启。

## 功能需求

### F1：记忆类型与作用域

- 支持用户偏好、纠正反馈、项目事实和参考资料四类记忆。
- 用户偏好默认属于用户级，可跨项目使用。
- 纠正反馈默认属于项目级；只有用户明确表达适用于所有项目时才允许保存为用户级。
- 项目事实和参考资料只属于当前项目。
- 项目记忆不得越过当前工作区边界；路径不同的项目彼此隔离。

### F2：候选提取

- 只在 Agent 成功完成一轮回答后考虑提取；取消、异常、空响应和未完成工具链不提取。
- 先使用不调用模型的本地信号检测，判断本轮是否可能包含偏好、纠正、稳定决定或参考资料。
- 只有命中信号后，才异步复用当前 Provider 和模型生成结构化候选。
- 提取只使用本轮用户文本、最终回答和当前活跃记忆的精炼索引，不使用工具结果、思考内容、会话摘要或 Provider 专属状态。
- 每轮最多产生三条候选。候选必须包含类型、作用域、标题、精炼内容、应用方式、来源和提出理由。
- 提取器只能输出候选，不能直接读写记忆文件。

### F3：人工确认

- 后台提取完成后先持久化候选，再等待 TUI 空闲时逐条展示。
- 用户可以确认、编辑后确认或拒绝候选。
- 新建、更新、合并和失效建议都必须确认后才改变长期记忆。
- 相同候选不得因恢复会话、界面重绘、程序重启或模型重复输出而重复出现。
- 拒绝候选不会形成长期记忆。

### F4：存储与使用

- 用户级记忆保存在 `~/.kcode/memory/`，项目级记忆保存在 `<workspace>/.kcode/memory/`。
- 每条已确认记忆使用带 YAML frontmatter 的 Markdown 文件，包含稳定标识、schema 版本、类型、作用域、状态、来源和时间信息。
- 每个作用域维护可从单条记录重建的 `MEMORY.md` 精炼索引；单条文件是审计来源，索引是运行时输入。
- 只把已确认且处于活跃状态的精炼索引注入现有 `long_term_memory` 提示词区段。
- 用户级和项目级内容合并后受固定字节和行数预算保护；溢出只警告和排除 Prompt 输入，不删除磁盘记录。
- 项目自动记忆默认被 Git 忽略。需要团队共享的稳定规范由用户整理进 `KCODE.md`。

### F5：记忆管理

- `Ctrl+M` 打开集中记忆面板，可查看待确认候选、活跃记忆、已失效记忆、治理建议和持续 warning。
- 用户可以编辑、恢复或把记忆标为失效。
- 默认清理方式是可恢复的失效；永久删除只允许由用户主动触发，并需要独立二次确认。
- 生成中或存在其他 Modal 时，记忆面板和候选弹窗不能抢占当前交互。

### F6：记忆治理

- 用户级和项目级记忆分别治理。
- 只有某作用域同时满足至少十条活跃记忆、距上次治理至少二十四小时、并新增至少五个完成会话时，才在后台检查重复、冲突和可能过期的内容。
- 治理只能生成更新、合并或失效建议，不能生成永久删除动作，也不能跨作用域合并。
- 所有治理建议复用候选确认流程；未经确认不得改变记忆。

### F7：启用与费用保护

- 长期记忆默认关闭，用户必须在用户级配置中显式开启。
- 项目配置可以关闭长期记忆，但不能替用户从关闭提升为开启。
- 配置和用户文档必须说明额外模型调用、本地明文存储及关闭方式。
- 提取和治理复用当前 Provider 和模型，不增加厂商专属后台状态或独立凭据。

## 非功能需求

### N1：安全

- 记忆是本地明文文件，目录和文件必须收紧权限，但不承诺加密。
- 写入前必须脱敏 KCode 已知敏感值，并阻止常见密钥、私钥和凭据赋值形态进入候选核心内容。
- 系统必须明确说明无法识别任意秘密。
- 记忆路径、锁文件和临时文件必须执行边界校验并拒绝符号链接越界。

### N2：可靠性

- 文件写入使用跨进程锁、同目录临时文件、flush、fsync 和原子替换。
- 索引损坏或被手工修改时，可以从有效单条记录重建。
- 单个坏文件或单个作用域失败不能阻塞另一个作用域和正常聊天。
- 后台任务可取消且关闭有界，不能留下半写文件或无限等待。

### N3：厂商无关

- 长期记忆数据不保存 Provider continuation state、SDK 对象或厂商专属响应格式。
- 提取与治理通过现有统一 Provider 接口运行，并使用严格的 KCode 本地 schema 校验结果。

### N4：可审计与可逆

- 每条记忆都可以追踪到来源 session 和 turn 指纹。
- 所有模型建议在应用前可见。
- 除用户二次确认的永久删除外，状态变化可恢复。

## 不做的事

- 不实现向量数据库、Embedding 或语义 RAG。
- 不自动批准、自动更新、自动合并、自动失效或自动删除长期记忆。
- 不实现云同步、团队同步或加密存储。
- 不从一期旧会话批量回填长期记忆。
- 不授予模型任意访问用户目录文件的能力。
- 不使用长期记忆替代 `KCODE.md`、会话 JSONL 或上下文压缩摘要。
- 不新增 `/memory` 等 slash command。

## 验收标准

- AC1：四类记忆和作用域判断均有测试，项目记忆不会跨工作区加载。
- AC2：未命中本地信号时不增加 Provider 调用；命中后只发送允许的本轮内容和精炼索引。
- AC3：确认、编辑确认、拒绝、失效、恢复和永久删除流程均可观察并有测试。
- AC4：候选跨重启保留且去重，未经确认不会进入活跃索引。
- AC5：用户级和项目级 Markdown 记录、权限、锁、原子写、坏文件隔离和索引重建均有测试。
- AC6：只把已确认且活跃的记忆注入 `long_term_memory`，预算溢出不删除磁盘记录。
- AC7：治理阈值、失败节流、作用域隔离和绝不自动删除均有集成测试。
- AC8：Provider、解析、权限或存储失败不阻断正常聊天与一期会话持久化，并显示明确 warning。
- AC9：FakeProvider 端到端证明“对话 → 候选 → 重启 → 确认 → 新会话自动使用”流程。
- AC10：最终通过 compileall、ruff、完整 pytest 和 diff 检查，版本升级至 `0.7.0`。
