# KCode 上下文管理 Spec

## 背景

KCode 是一个无状态的 LLM Agent：每轮与模型交互时，Provider 都需要收到本轮请求可见的消息、工具调用和工具结果。随着编码任务持续执行，历史中的文件内容、命令输出和搜索结果会不断累积，导致请求延迟和输入 Token 成本上升，最终可能触发 Provider 的 `prompt_too_long` 错误。

工具结果通常是上下文增长的主要来源，但它们并不具有相同的长期价值：某些结果只用于当前一步，某些结果需要保留原文供后续精确读取，某些结果则应被提炼为当前任务状态。仅依靠增加模型上下文窗口不能解决信息密度下降的问题；上下文长度本身也可能降低模型表现。

KCode 已经具备 Agent Loop、权限引擎、MCP 客户端和多 Provider 支持。本章只实现记忆层的上下文管理组件，不改变工具语义、权限边界、Provider 协议和 Agent 的核心停止条件。

上下文管理采用两层机制：第一层是无 LLM 的确定性 Artifact 外置，处理单个或单批工具结果；第二层是有 LLM 成本的结构化 Context Compaction，处理整体历史。两层共享原始事实和 Artifact 索引，但职责独立。

## 目标

- G1：在单进程会话内支持长时间 Agent 任务，正常情况下不因上下文超过 Provider 限制而中断。
- G2：优先减少低价值工具结果占用的模型可见上下文，同时保留可按需恢复的原始 Artifact。
- G3：通过结构化工作记忆提高当前上下文的信息密度，而不是只追求 Token 数下降。
- G4：用户原始消息和工具原始事实在会话的规范记录中保持可追溯；摘要只作为模型当前可见的工作记忆。
- G5：自动压缩、手动 `/compact` 和 `prompt_too_long` 紧急恢复共享摘要核心路径，但触发条件、用户反馈和熔断行为相互独立。
- G6：不同 Provider 的 Token usage 统一为上下文输入预算、缓存信息、输出预留和估算置信度，避免机械相加造成错误判断。
- G7：保持请求前缀稳定，使 Provider 具备获得 Prompt Cache 命中的条件；不把缓存命中视为功能正确性的前提，也不保证 Provider 必然命中。
- G8：上下文管理集中在专属模块内，对 Agent 主循环暴露窄接口；关闭上下文管理时，既有 Agent 行为保持不变。

## 核心概念

### 规范记录与模型视图

系统必须区分两类状态：

- 规范记录：当前进程内追加保存的原始用户消息、助手消息、工具调用、工具结果和压缩事件，是事实和恢复依据；Context Compaction 不得用摘要覆盖或删除其中的原始消息。
- 模型视图：下一次 Provider 请求实际可见的消息、恢复段和工具集合，可以通过第一层外置和第二层压缩重建。

压缩只改变模型视图，不改变规范记录和已经落盘的 Artifact。

### Artifact

Artifact 是工具结果的本地、可追溯表示，至少包含工具调用 ID、工具名、创建时间、原始字节数、结果状态、保存路径和脱敏后的完整内容。Artifact 保存的内容必须是已经经过 KCode 敏感值脱敏、可以安全进入模型上下文的版本，不得把未脱敏 Provider Key 或 MCP 凭据写入磁盘。

Artifact 不是语义摘要。预览是机械截取，结构化摘要是 LLM 生成的工作记忆，三者必须在消息中明确区分。

### Prompt Cache

Prompt Cache 是 Provider 对重复请求前缀的计算复用，用于降低输入处理成本和延迟。它不是会话记忆、不是摘要，也不是 Artifact 存储。

“写入即终态”可以保持历史前缀稳定并提高获得缓存命中的机会，但 Provider、模型、TTL、请求格式和服务端负载仍可能导致未命中。

## 功能需求

### 第一层：确定性 Artifact 外置

> 本层不调用 LLM，不产生语义摘要。工具结果的 50000 和 200000 阈值、预览体的 2048 阈值均以 `len(content.encode("utf-8"))` 计算的 UTF-8 字节数为准；这些字节阈值只用于外置决策，不替代 Token 预算估算。

- F1：当单个工具结果超过 50000 字节时，系统必须先将完整的脱敏结果写入当前会话的 Artifact 路径，再在模型视图中使用稳定的预览替换体。
- F2：同一组工具结果的聚合内容超过 200000 字节时，系统必须在不破坏工具调用—工具结果配对和原始顺序的前提下，按结果字节数从大到小选择外置项，直到剩余模型可见内容不超过聚合阈值。
- F3：按字节大小选择只是一种确定性成本策略，不得被解释为信息价值排序。每个结果都必须保留工具名、调用 ID、状态、警告和 Artifact 引用等元数据；并列结果按原始工具调用顺序稳定排序。
- F4：单个结果和聚合结果的外置决策必须在工具结果进入模型视图前完成。决策完成后，该工具调用 ID 在本会话内不可从“保留原文”翻转为“外置”，也不可从“外置”翻转为“保留原文”。
- F5：预览替换体必须包含：原始字节数、前 20 行且不超过 2048 字节的头部预览、Artifact 路径或 ID、工具名和工具调用 ID、明确的重读提示。预览必须说明它不是完整结果。
- F6：同一工具调用 ID 的 Artifact 只能成功写入一次。后续请求组装必须复用同一份替换文本；不得重新生成时间戳、预览或路径导致历史前缀变化。
- F7：落盘、替换体生成和决策账本更新必须作为一个可观察的一致操作完成。任一步失败时，系统保持原文、不写入完成决策，并允许下一次请求重新尝试。
- F8：当模型通过文件读取工具读取本层 Artifact 时，读取必须支持按偏移量或范围读取。读取结果可以受普通工具结果限制，但本层 Artifact 的“读取回显”必须避免无条件重新指向同一 Artifact，保证模型能够获取所请求的片段。
- F9：第一层必须是无 LLM 的确定性处理。正常路径不得因为第一层而增加 Provider 请求，也不得在预览中声称未被实际读取的事实。

### 第二层：结构化 Context Compaction

- F10：当归一化后的上下文估算达到 `context_window - summary_output_reserve - automatic_safety_margin` 时，系统必须在下一次普通 LLM 请求前触发一次自动压缩。初始值为摘要输出预留 20000 Token、自动安全余量 13000 Token。
- F11：摘要请求不得传入工具定义，也不得执行工具调用。摘要请求必须明确要求只处理提供的历史内容，并禁止根据未提供的内容补全事实。
- F12：摘要不得要求或依赖 `<analysis>` 草稿作为硬性协议。摘要直接生成可解析的结构化工作记忆；如果 Provider 支持结构化输出，应使用结构化输出，否则使用固定标题和边界标记。
- F13：结构化工作记忆必须至少包含：任务目标、已确认事实、推测与未知项、关键决策、涉及的文件和代码位置、错误与修复、当前工作状态、未完成任务、下一步行动、Artifact 引用，以及 `history_incomplete` 状态。
- F14：摘要中的事实必须来自提供的历史或明确引用的 Artifact。无法确认的内容必须标为未知或推测，不得伪装成已完成、已验证或已读取。
- F15：用户原始消息不得在摘要中无限复制。规范记录继续保存原始用户消息；摘要只保留与任务状态有关的关键原文片段或消息引用，尤其要保留会影响实现的约束、偏好、否定和验收要求。
- F16：摘要完成后，系统必须从原模型视图尾部保留近期原文。按消息组从尾部倒序累加，直到估算 Token 至少达到 10000 且消息数至少达到 5；如果达到历史末尾则保留全部可用消息。不得切开工具调用和对应工具结果。
- F17：摘要必须明确声明它覆盖的历史范围。若摘要请求因为自身超长而丢弃了旧消息组，必须设置 `history_incomplete=true`，不得声称覆盖了未提供的历史；规范记录和已存在 Artifact 不得因此删除。
- F18：摘要压缩后的模型视图必须按以下顺序组织：结构化工作记忆、恢复段、近期原文。恢复段不得伪造原始消息，所有恢复内容必须标明来源和可能的截断。

### 压缩后恢复

- F19：第二层完成后，恢复段必须包含最近成功读取的文件快照、下一次请求实际可用的工具说明索引和边界提示。
- F20：最近文件快照最多保留 5 个，按最后一次成功读取时间倒序排列；单个快照最多保留约 5000 Token 的头部片段，并标记读取时间、文件路径和截断状态。快照是历史读取时的副本，不得被描述为当前文件最新内容。
- F21：恢复段列出的工具集合必须与同一轮普通 LLM 请求传给 Provider 的工具集合一致，包括工具数量、名称和参数 Schema。摘要请求本身仍不得传工具定义。
- F22：边界提示必须告知模型：摘要和快照可能被截断；需要精确文件内容、完整错误或用户原话时，必须重新读取来源，不得依据摘要脑补代码。
- F23：每次文件工具成功返回原始内容后，系统必须更新文件追踪状态；追踪状态与工具结果回填必须在同一个 Agent 主循环任务中按确定顺序完成。
- F24：文件追踪、Artifact 决策账本和自动压缩熔断计数必须在并发访问时保持一致；不得出现已记录工具调用 ID 但没有对应替换文本或 Artifact 的中间状态。

### Token 预算与 Provider usage

- F25：系统必须定义 Provider 无关的归一化 usage，至少区分：上下文输入 Token、缓存命中或写入 Token、输出 Token、输出预留 Token、估算值和估算置信度。
- F26：Provider 适配器负责解释原始 usage 字段。上下文管理器不得假设 `input`、`cache_read`、`cache_creation` 和 `output` 在所有 Provider 中可以直接相加；缓存 Token 不得被重复计入上下文输入 Token。
- F27：每次真实 LLM 请求完成后，系统优先使用 Provider 返回的归一化上下文输入 usage 更新锚点。两次真实请求之间，只对锚点之后新增的消息按 `字符数 / 3.5` 进行近似增量估算，并记录该估算为近似值。
- F28：预算判断必须同时考虑模型上下文窗口、系统提示、工具定义、当前消息和预留输出空间。`context_window` 优先取显式配置，其次取模型元数据，最后使用 Provider 的保守默认值；默认值不得被描述为所有同协议模型的真实窗口。
- F29：如果 usage 缺失、字段非法或 Provider 无法归一化，系统必须标记估算置信度降低并使用安全余量，不得把未知 usage 当作零。

### Prompt Cache 与前缀稳定

- F30：上下文管理必须把 Prompt Cache 视为可选的 Provider 优化能力，而不是正确性依赖。
- F31：第一层成功外置后，替换体、Artifact 路径、消息顺序和元数据必须稳定；同一历史前缀不应因重复组装而发生无意义变化。
- F32：第二层压缩允许改变旧历史，因此可能使旧缓存从压缩点开始失效；压缩后的新前缀可以在后续请求中重新获得缓存。
- F33：系统不要求自动报告缓存命中率，但 Provider 适配器必须允许保留和展示缓存 usage；缓存未命中不得触发功能重试或错误。

### 手动入口

- F34：TUI 输入以斜杠开头的内容必须走本地命令路径，不发送给 LLM。已有 `/exit`、`/plan`、`/do` 命令继续保持原行为，并新增 `/compact`。
- F35：未知命令只显示可用命令提示，不写入规范记录，不访问 Provider。
- F36：`/compact` 跳过自动阈值和自动熔断，无条件触发一次第二层摘要；本次手动动作不额外执行第一层，但下一次普通请求仍执行常规第一层检查。
- F37：手动压缩完成后，TUI 必须展示压缩原因、压缩前后估算值、估算置信度和是否发生历史不完整截断。
- F38：手动压缩与 Agent 主循环不得并发修改同一模型视图；系统必须等待当前 Agent 轮次结束，或使用会话级互斥保证操作顺序。

### 异常路径与熔断

- F39：普通请求收到 `prompt_too_long` 类错误时，系统必须先执行一次紧急第一层外置，再执行第二层摘要，并用新的模型视图重试原请求一次。
- F40：紧急压缩成功后，系统必须重新计算上下文预算；如果仍无法在安全余量内容纳请求，则直接报告不可恢复错误，不进行第二次紧急压缩。
- F41：紧急压缩后的普通请求最多重试一次；再次收到 `prompt_too_long` 时按正常错误流程结束当前请求。
- F42：摘要请求自身过长时，系统可以按“用户提交 + 一组助手/工具往返”丢弃最旧消息组后重试。每次丢弃都必须记录范围；摘要成功时设置 `history_incomplete`，摘要失败时不得修改规范记录。
- F43：自动摘要连续失败 3 次后，自动路径进入熔断，不再自动触发摘要；任何一次自动摘要成功都清零连续失败计数。
- F44：手动 `/compact` 和紧急压缩绕过自动熔断，但仍受单次请求和并发互斥限制。

### 配置与生命周期

- F45：每个 Provider 配置项支持可选的 `context_window`，单位为 Token，类型为正整数。
- F46：未配置 `context_window` 时，系统按“模型元数据 → Provider 保守默认值”顺序解析，并在无法确认真实窗口时降低估算置信度。
- F47：示例配置必须展示 `context_window`，但单条结果阈值、聚合阈值、摘要预留、安全余量、近期原文保留量和熔断次数保持内部常量，不作为本章配置项。
- F48：进程启动时生成一次会话 ID，格式为 `<unix_ts>-<short_random>`；所有 Artifact 写入 `.kcode/sessions/<session_id>/tool-results/<tool_use_id>`，目录按需创建，进程退出后不自动清理。
- F49：上下文管理关闭或从未触发时，既有工具、历史、权限、取消、Provider 流和 TUI 行为不得改变。

## 非功能需求

- N1：第一层的决策和预览生成必须是确定性的；常规路径不调用 LLM。落盘 I/O 不得长时间阻塞异步事件循环。
- N2：Artifact 必须使用已脱敏内容；路径、日志、预览、错误、摘要和 TUI 不得泄漏 API Key、MCP 凭据或其他敏感值。
- N3：规范记录、Artifact、模型视图和结构化摘要之间必须有可追溯关系；摘要失败不得覆盖规范记录，落盘失败不得让 Agent 进程崩溃。
- N4：上下文管理不得改变工具调用顺序、工具结果顺序、工具调用—工具结果配对、权限裁决、只读并发、副作用串行和取消语义。
- N5：核心逻辑必须可脱离真实 Provider 单元测试；默认测试不联网、不调用真实模型、不产生费用。
- N6：每次压缩必须产生可观察事件，至少包含触发原因、估算前后值、估算置信度、外置结果数量、摘要是否完整和失败原因。
- N7：usage 归一化必须能覆盖 Anthropic、OpenAI、DeepSeek 及未来兼容 Provider；缺失字段保持未知，不按零污染累计值。
- N8：摘要输出必须区分已确认事实、推测和未知内容，并保留 Artifact 或规范记录引用。
- N9：压缩质量不能只由 Token 降幅衡量；测试和人工验收必须覆盖压缩后的任务延续、文件定位、错误恢复和精确内容重读。
- N10：本章只保证单进程会话内的上下文管理，不实现跨进程会话恢复、跨 Agent 共享记忆或机器学习压缩策略。

## 不做的事

- 不直接集成 MemGPT 或 Letta 的完整 Agent Runtime；只借鉴分层记忆、外部 Artifact 和按需恢复思想。
- 不在第一层调用摘要模型，不为每个大工具结果生成语义摘要。
- 不要求摘要模型生成或持久化隐藏推理草稿；摘要直接输出结构化工作记忆。
- 不把 Prompt Cache 当作可靠存储、上下文恢复机制或功能正确性的前提。
- 不强制接入精确 Tokenizer；本章使用 Provider usage 锚定和新增内容近似估算，但保留未来替换估算器的接口。
- 不做摘要质量的机器学习反馈优化、在线 A/B 或自动 Prompt 搜索。
- 不自动删除 Artifact、规范记录或 `.kcode/sessions/` 会话目录。
- 不做跨进程或跨会话的完整对话恢复。
- 不支持同一进程内多个 Agent 实例共享上下文管理状态。
- 不改变既有工具、MCP、权限、Provider、Skill、计划模式和 Agent Loop 的业务语义。

## 验收标准

- AC1：单个工具结果超过 50000 字节时，模型视图只出现稳定预览和 Artifact 引用；Artifact 保存脱敏完整结果，预览包含字节数、路径、调用 ID 和重读提示。
- AC2：同一批工具结果总量超过 200000 字节时，系统按字节从大到小、同字节按原始顺序选择外置项，并保持调用—结果配对和结果顺序。
- AC3：对同一 `tool_use_id` 重复组装请求时不重复写文件，替换字符串逐字节一致；落盘失败时不写完成账本，下一次仍可重试。
- AC4：第一层测试抓取 Provider 调用次数，确认单条外置和聚合外置都不触发 LLM 摘要请求。
- AC5：摘要请求不包含工具定义、不产生工具调用，并直接得到可解析的结构化工作记忆。
- AC6：结构化摘要至少能表达目标、确认事实、推测、未知项、决策、失败、当前状态、待办、下一步、Artifact 引用和 `history_incomplete`。
- AC7：摘要不得把未出现在输入历史或 Artifact 中的内容写成已确认事实；摘要失败时规范记录和 Artifact 保持不变。
- AC8：摘要后保留近期原文，估算 Token 至少达到 10000 且消息数至少达到 5，或已经到达历史开头；工具调用与结果不得被拆开。
- AC9：最近读取的 7 个文件经过压缩后只恢复最后 5 个，每个快照带路径、时间戳、截断标记，并明确不是当前文件最新状态。
- AC10：恢复段列出的工具集合与下一次普通请求实际传给 Provider 的工具集合完全一致；摘要请求仍不传工具。
- AC11：Provider 返回不同格式的 usage 时，归一化结果不会重复计算缓存 Token，也不会把未知字段当作零；缺失 usage 时估算置信度降低。
- AC12：配置 `context_window: 100000` 时，自动阈值按上下文窗口、摘要输出预留和自动安全余量计算；未配置时使用模型元数据或保守 Provider 默认值。
- AC13：同一稳定历史在重复请求组装后保持逐字节相同；测试只验证缓存资格条件，不断言 Provider 必然命中缓存。
- AC14：输入 `/compact` 时不发普通对话请求，自动阈值和熔断不阻止摘要；完成后 TUI 展示压缩前后估算、置信度和历史完整性。
- AC15：Provider 在普通请求中返回 `prompt_too_long` 时，系统最多执行一次紧急压缩和一次普通请求重试；重试再次失败时不继续循环。
- AC16：摘要自身过长时按消息组重试；摘要成功但丢弃过历史时设置 `history_incomplete=true`，规范记录不被删除。
- AC17：自动摘要连续失败 3 次后自动路径熔断；成功一次后清零；手动和紧急路径不受自动熔断影响。
- AC18：模拟一个“压缩前能完成、压缩后仍需读取 Artifact 才能完成”的编码任务，验证模型可通过 Artifact 路径找回精确文件片段、继续待办并恢复错误上下文。
- AC19：模拟用户约束、已确认事实、推测和未知信息同时存在的会话，验证摘要不会把推测转换为事实，用户的关键原文约束仍可恢复。
- AC20：验证工具、权限、取消、并发调度、MCP、计划模式和普通聊天的既有测试在上下文管理关闭和未触发场景下全部不退化。
- AC21：所有默认测试不访问真实网络、不读取真实 API Key、不产生费用；日志和 TUI 输出不包含敏感值。
