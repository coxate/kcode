# KCode 上下文管理：面试准备

## 1. 一句话介绍

我为 KCode 实现了一套两层上下文管理机制：先用确定性的 Artifact 外置减少大型工具结果占用，再在接近模型窗口上限时用 LLM 生成结构化工作记忆，同时保留不可变的原始会话记录，保证长任务可以压缩、恢复和继续执行。

## 2. 30 秒项目介绍

KCode 的每次模型请求都要携带历史消息，长时间执行后，工具输出会迅速挤占上下文窗口。我没有直接删除旧消息，而是把系统分成三类数据：完整的规范记录、可恢复的 Artifact，以及真正发给模型的 ContextSnapshot。第一层只做确定性的工具结果外置，不调用 LLM；第二层才调用当前 Provider 生成结构化摘要，并保留近期原文和恢复提示。这样即使摘要遗漏或失败，事实来源仍然存在。系统还加入了 Token 预算估算、三次失败熔断、`prompt_too_long` 单次紧急压缩重试，以及 `/compact` 手动入口。

## 3. 递进学习路线

### 第一阶段：先讲清问题

- LLM 通常是无状态的；所谓“记忆”，本质上是应用在每次请求前重新组装上下文。
- 上下文窗口同时容纳系统提示、历史消息、工具定义、工具结果和本轮输出预留。
- 编码 Agent 中最容易膨胀的通常不是用户消息，而是日志、搜索结果和文件内容等工具输出。

### 第二阶段：掌握两个压缩层

#### 第一层：Artifact 外置

- 单个工具结果超过 50,000 字节，或同批工具结果合计超过 200,000 字节时触发。
- 完整、脱敏后的结果原子写入 `.kcode/sessions/<session_id>/tool-results/`。
- 模型视图只保留稳定预览、工具名、调用 ID、字节数、路径和重新读取提示。
- 这一层不调用 LLM，也不产生语义摘要，因此成本低、结果稳定、可重复。

“优先外置较大结果”只是容量治理策略，不代表大结果价值低。为避免不稳定，相同大小按原始调用顺序处理，并保护工具调用与工具结果的配对关系。

#### 第二层：Context Compaction

- 当预算接近窗口上限时，调用当前 Provider 生成结构化工作记忆。
- 摘要请求固定不提供工具，并使用 `tool_choice="none"`，避免压缩过程执行外部操作。
- 摘要区分已确认事实、推测和未知项，并记录决策、文件位置、错误、当前状态、待办、下一步和 Artifact 引用。
- 最终模型视图为“结构化摘要 + 恢复段 + 近期原文”。
- 规范记录不被覆盖；摘要失败时继续保留旧模型视图。

### 第三阶段：理解三类状态

| 状态 | 作用 | 是否是事实来源 |
| --- | --- | --- |
| `Conversation` | 保存完整用户消息、助手消息和工具交互 | 是 |
| Artifact | 保存被外置的完整、脱敏工具结果 | 是 |
| `ContextSnapshot` | 本次 Provider 请求实际看到的模型视图 | 否，是可重建视图 |

关键设计原则是：**事实来源与模型工作记忆分离**。摘要可以有损，但不能成为唯一副本。

### 第四阶段：预算与 Prompt Cache

- `context_window` 的来源顺序是显式配置、模型元数据、64,000 的保守默认值。
- 有真实 Provider usage 时建立锚点；后续增量用字符数除以 3.5 近似估算。
- 缓存读写 Token 单独记录，不能再次加入上下文输入，否则会重复计算。
- Prompt Cache 是 Provider 对稳定请求前缀的复用优化，不是长期记忆，也不能保证命中。
- 稳定的 Artifact 替换文本、消息顺序、工具 Schema 和系统前缀有利于缓存命中，但正确性不能依赖缓存。

### 第五阶段：失败恢复

- 自动摘要连续失败三次后熔断，防止每轮都重复调用模型。
- 手动 `/compact` 和紧急压缩不受自动熔断限制。
- Provider 返回 `prompt_too_long` 时，只紧急压缩并重试一次；再次失败立即结束，避免递归重试。
- 摘要输入如果不得不丢弃部分历史，必须标记 `history_incomplete=true`，不能假装覆盖了全部记录。

## 4. 代码地图

- `src/kcode/context/models.py`：上下文预算、快照、压缩结果等数据模型。
- `src/kcode/context/artifacts.py`：Artifact 的脱敏、原子写入、幂等复用和范围读取。
- `src/kcode/context/ledger.py`：冻结外置决策并保证排序稳定。
- `src/kcode/context/usage.py`：Provider usage 归一化与增量估算。
- `src/kcode/context/compaction.py`：无工具的结构化摘要请求与解析校验。
- `src/kcode/context/manager.py`：协调外置、预算判断、压缩、恢复段和并发保护。
- `src/kcode/orchestration.py`：在 Agent 请求组装处接入 ContextSnapshot，并处理紧急重试。
- `src/kcode/commands/`、`src/kcode/ui/app.py`：提供 `/compact` 手动命令及结果展示。

## 5. 高频面试问答

### Q1：为什么采用两层，而不是每轮都让 LLM 摘要？

第一层处理的是“体积问题”，适合用确定性规则解决；第二层处理的是“语义连续性问题”，才需要 LLM。每轮摘要会增加费用和延迟，还会持续累积摘要误差。两层设计让大多数请求只付出本地 I/O 成本。

### Q2：第一层为什么不生成摘要？

工具结果通常需要精确恢复，例如报错栈、代码和搜索结果。第一层保存完整内容，只在模型视图中替换为可追踪预览，避免 LLM 改写事实。语义压缩留给接近窗口上限时的第二层。

### Q3：按大小优先外置会不会丢掉重要信息？

不会直接丢失，因为完整内容仍在 Artifact 中。但模型暂时看不到全文，可能忽略其中的重要细节。因此替换文本必须带来源、路径和重读提示，第二层也要保留 Artifact 引用。未来可以加入“大小 + 价值”的策略，但当前规则更稳定、容易测试。

### Q4：为什么不直接用摘要替换 `Conversation`？

摘要是有损信息，可能遗漏路径、参数或失败原因。如果覆盖原记录，就无法审计和恢复。KCode 只改变发给模型的视图，规范记录保持不可变，使压缩失败和模型幻觉都不会破坏事实来源。

### Q5：摘要如何处理第一层已经外置的内容？

摘要主要看到稳定预览和 Artifact 元数据，不应凭空补全 Artifact 全文。它记录 Artifact 引用；需要精确内容时，恢复段要求模型重新读取。这样既节省 Token，又保持按需恢复能力。

### Q6：Prompt Cache 和上下文压缩是什么关系？

上下文压缩解决“请求是否放得下和任务能否继续”，Prompt Cache 解决“相同前缀能否少算一些费用和延迟”。缓存失效不应影响正确性。稳定前缀只是提高缓存资格，不保证 Provider 一定命中。

### Q7：为什么摘要请求必须禁用工具？

压缩属于请求组装阶段，不应该读取文件、修改代码或产生新的工具结果。禁用工具可以防止副作用、递归上下文增长和权限绕过，让压缩成为纯粹的数据转换。

### Q8：Token 为什么不直接按字符数计算？

字符比例只适合低成本近似，不同语言和 Provider 的分词差异很大。因此 KCode 优先使用上一次真实 usage 作为锚点，只对新增内容估算，并显式记录置信度。生产环境可进一步接入各模型 tokenizer。

### Q9：缓存 Token 为什么不能重复计入上下文输入？

缓存读 Token 通常表示输入中的一部分被缓存命中，不是额外发送的一份上下文。如果把 input tokens 和 cached tokens 再相加，会高估请求长度并过早压缩。

### Q10：如何避免摘要失败造成死循环？

自动摘要连续失败三次后熔断；失败不覆盖旧视图；`prompt_too_long` 只允许一次紧急压缩和一次原请求重试。三个限制共同保证失败路径有明确终点。

### Q11：如何保证并发安全和幂等性？

会话级锁防止同一会话同时修改压缩状态；Artifact 使用稳定路径和原子替换；OffloadLedger 冻结已做出的替换决定。因此相同输入重复组装时可以得到逐字节稳定的替换文本。

### Q12：你怎样测试这套系统？

单元测试覆盖 Artifact 外置、稳定排序、脱敏、摘要结构、usage 归一化、熔断和紧急重试；集成测试验证规范记录不变、工具调用结果不拆分和 `/compact` 不发送普通请求。真实模型还需要人工回归，观察压缩后能否继续定位文件、恢复错误和完成待办。

### Q13：为什么 MCP 会出现在上下文管理的讨论里？

上下文功能不要求修改 MCP。两者的交点只有：MCP 工具结果也可能很大，且 MCP 凭据必须在 Artifact 落盘前脱敏；另外本次工作树中 MCP 与上下文改动碰巧修改了同一批配置和 UI 文件，所以提交时必须按行拆分，不能把它们混成一个 commit。

### Q14：这套方案还有什么局限？

字符估算不如精确 tokenizer；按大小外置不了解语义价值；摘要质量仍依赖模型；Artifact 生命周期和磁盘配额还可以完善。后续可加入检索式记忆、价值评分、摘要版本评估和自动清理策略。

## 6. 人工测评脚本

人工测评不是替代单元测试，而是验证“压缩后模型还能不能把任务做好”。可以准备一个临时仓库，按以下步骤操作：

1. 让 KCode 阅读多个文件，定位一个跨文件问题并列出待办。
2. 制造足够长的工具输出，确认 `.kcode/sessions/` 下出现 Artifact。
3. 执行 `/compact`，记录压缩前后 Token、置信度和 `history_incomplete`。
4. 追问之前确认过的事实，检查模型是否区分事实、推测和未知项。
5. 要求继续完成未完成任务，观察文件定位、错误恢复和待办延续是否正确。
6. 询问 Artifact 中的精确内容，确认模型会重新读取，而不是根据摘要猜测。

建议记录以下指标：任务是否完成、关键事实准确率、Artifact 重读成功率、压缩次数、额外延迟、摘要失败次数和人工发现的幻觉数量。

## 7. 面试前自检

- 能否在 30 秒内说明为什么工具结果是 Token 大头？
- 能否画出 `Conversation → ContextManager → ContextSnapshot → Provider`？
- 能否解释 Artifact 与摘要分别解决什么问题？
- 能否说明 Prompt Cache 为什么不是记忆系统？
- 能否讲出两个失败保护：三次熔断和单次紧急重试？
- 能否诚实说明当前局限，并给出可验证的改进方向？

## 8. 推荐回答结构

面试中可以按“问题—约束—设计—失败保护—验证—局限”回答：先说明上下文会被工具结果撑爆，再说明两层方案和三类状态，然后讲熔断、紧急重试与测试，最后主动指出估算和语义价值判断仍可改进。这样比只罗列类名更能体现工程判断。
